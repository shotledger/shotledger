| 2026-09-02 | **Code license decided: AGPL-3.0-or-later + a contributor CLA**, once the repo goes public (still private, no urgency). AGPL over plain GPL specifically because ShotLedger has an optional Cloudflare Workers sync backend — GPL's copyleft triggers only on distributing a binary, so a hosted fork of the backend would owe nothing back; AGPL §13 closes that by extending the trigger to network use. The CLA (not the license itself) is what keeps the maintainer able to dual-license or grant an App Store exception later, since a copyright holder is never bound by their own license, but is bound once a second contributor's AGPL-covered patch lands without an assignment. LGPL and plain "noncommercial" framing were considered and rejected: LGPL is for libraries linked into other programs (the opposite problem — it exists to let proprietary software depend on open code, and ShotLedger isn't a library); a literal "commercial use only by the maintainer" clause exists (PolyForm Noncommercial/Shield) but is source-available, not OSI open source, and was rejected in favor of staying real open source. No AGPL clause, on its own, can technically stop a third party from recompiling the open client and calling the backend directly — see the next row                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

| 2026-09-03 | **Vault opt-in mechanism: passphrase re-wrap** (`feat/export-scope-vault-optin`), option (a) of the three considered. The Vault key is generated in and held by `expo-secure-store` (Android Keystore / iOS Keychain) and **cannot leave the device**, so copying Vault ciphertext into a bundle would produce a section no other device — and not even the same device after a reinstall — could ever decrypt. Rejected (b) shipping the key alongside the ciphertext: it makes the bundle exactly as sensitive as the Vault with nothing protecting it, and a bundle travels through share sheets, cloud folders and mail. Rejected (c) refusing outright: (a) turned out feasible. Export decrypts each document with the device key **in memory**, packs index + documents into one payload, derives a 32-byte key from the user's passphrase with PBKDF2-HMAC-SHA256 (fresh 16-byte salt, iteration count and salt recorded in the manifest, passphrase never), and seals the payload with the **existing Vault AES-256-GCM envelope**; restore re-seals every document under the receiving device's own key. **PBKDF2 is hand-written in `shared/src/backup/{sha256,pbkdf2}.ts`** because `expo-crypto`'s only hashing is an async whole-message `digest()` — one native round trip per call, so an HMAC costs two and any realistic iteration count would be hundreds of thousands of bridge crossings; no hashing library is in the lockfile and rule 2 forbids adding one unasked. That code is a hash and a KDF, not a cipher: confidentiality still rests entirely on native, reviewed AES-GCM, and the implementation is verified byte-for-byte against OpenSSL across every input length at the block/padding boundaries, randomised inputs up to 2 MB, and the published FIPS 180-4 / RFC 4231 / RFC 7914 vectors. Since #71 the Vault holds photographs of weapon licence cards, which is what the warning names: inclusion is off on every export with no remembered preference, and the on-screen warning must be acknowledged before the passphrase fields even become editable. **Restore merges the Vault, never replaces it** — unlike the database, which stays a full replace — because a document that exists only on this device would otherwise be destroyed unrecoverably; documents are keyed by uuidv7 id, so restoring the same bundle twice is idempotent. A wrong passphrase is detected before anything is written. The container byte layout is unchanged (`BACKUP_CONTAINER_FORMAT_VERSION` stays 1): the Vault is one more named entry plus one **optional** manifest field, so pre-Vault bundles still restore and newer bundles still parse in older builds                                                                                                                                                                                                                                                                                                                                      |
